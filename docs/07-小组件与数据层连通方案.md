# 桌面小组件与主 App 数据层的连通方案

**文档版本**：v1.0（第 11 阶段产出，对应提交 #11）
**模块**：`widget`（P1 伴生模块）

---

## 1. 模块依赖关系（本阶段的实际实现）

```
:app  ──► :widget ──► :core-data ──► :core-domain
  │                        ▲
  └────────────────────────┘
```

**与 docs/03 的差异及原因**：原设计写「app 与 widget 互不依赖」，但那是**多 APK** 场景下的写法。
本项目交付**单个 APK**，而 Android 的 library manifest 只有在被 app 依赖时才会合并进最终清单——
否则 `<receiver>` 根本不会出现在 APK 里，桌面小组件列表里也看不到它。

所以本阶段调整为：

| 关系 | 结论 |
|---|---|
| `:app → :widget` | **必需**：打包和清单合并 |
| `:widget → :core-data` | **必需**：读数据库 |
| `:widget → :app` | **禁止**：组件模块不引用任何 app 类（见下条） |
| 循环依赖 | 不存在 |

**为什么 widget 不能反向依赖 app**：组件运行在桌面启动器的广播回调里，如果它引用了 app 的
Activity/ViewModel，就等于把整个 UI 层拖进组件的执行路径；一旦 app 侧改动，组件也要跟着重编。

**点击跳转怎么做到不依赖 app**：用**显式类名字符串**构造 Intent。

```kotlin
private const val MAIN_ACTIVITY = "com.dancijiyi.app.MainActivity"

Intent().apply {
    setClassName(context.packageName, MAIN_ACTIVITY)
    flags = FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_CLEAR_TOP
}
```

代价是「改名时编译器不会提醒」，所以这里用常量 + 注释锁定契约；若将来要更强的约束，
可以改用一个 `:core-navigation` 模块只放路由常量。

## 2. 数据层连通方案

### 2.1 同一进程、同一进程内单例

```
桌面启动器 ──广播──► DueWordWidgetProvider(运行在 app 进程)
                          │
                          ▼
              DataFactory.wordRepository(context, clock)
                          │
                          ▼
              DancijiyiDatabase.get(context)  ← 进程内 @Volatile 单例
                          │
                          ▼
                   /data/data/<pkg>/dancijiyi.db
```

关键点：
- `AppWidgetProvider` 是**广播接收器**，不是独立进程。它运行在主 App 的进程里（除非在
  manifest 里显式写 `android:process`，本项目没有写），所以能直接拿到同一个
  `DancijiyiDatabase` 实例；
- 主 App 与小组件**不需要** ContentProvider、不需要 AIDL、不需要跨进程同步；
- 因此不存在「App 里改了数据、组件还是旧数字」这类经典问题——它们读的是同一份 SQLite。

### 2.2 为什么走 `DataFactory` 而不是直接用 `Dao`

`:core-data` 把 Room 作为 `implementation` 依赖，不向外部暴露 `RoomDatabase` 类型。
`widget` 只能看到 `WordRepository` 这类**领域接口**（第 8 阶段引入的 `DataFactory`）。
好处：换持久化实现时，组件代码一行不用改。

### 2.3 读取方式：`Flow.first()` 而不是 `observe`

组件是无状态的一次性刷新，不需要持续订阅：

```kotlin
val repository = DataFactory.wordRepository(context, Clock.systemDefaultZone())
val dueCount = repository.observeDueCount(Instant.now()).first()
```

`observeDueCount` 返回的是 `Flow<Int>`，`first()` 取首个发射值即当前到期数。
**为什么不长订阅**：广播回调的生命周期只有几秒，挂一个常驻 Flow 会在组件卸载后泄漏。

## 3. 刷新链路设计（本阶段实现 ①②，③④ 留到第 12 阶段）

| # | 触发源 | 时机 | 状态 |
|---|---|---|---|
| ① | 系统 `onUpdate` | 添加组件、开机、时区变更、每 30 分钟 | ✅ 已实现 |
| ② | 主 App 启动 | 种子数据写入后主动刷新一次 | ✅ 已实现 |
| ③ | 主 App 写库后 | 导入完成、作答结算后立即刷新（≤1s） | ⏳ 第 12 阶段 |
| ④ | WorkManager 跨天 | 每日 00:05 把计数归零 | ⏳ 第 12 阶段 |

> `updatePeriodMillis` 的**系统最小间隔就是 30 分钟**，且系统会做 Doze 批处理，
> 所以「实时」这件事不能靠它，必须靠 ③ 主动触发。

### 3.1 主动刷新接口

```kotlin
// widget 模块提供
DueWordWidgetProvider.requestUpdate(context)

// 主 App 侧调用（本阶段：种子写入后）
runCatching { DueWordWidgetProvider.requestUpdate(this) }
```

内部实现：取所有实例 id → 发一个带 `EXTRA_APPWIDGET_IDS` 的 `APPWIDGET_UPDATE` 广播 →
走回 `onUpdate` → 重新查询并渲染（幂等，可安全重复调用）。

## 4. 线程模型与 ANR 防护

`onUpdate` 在主线程执行，系统给的预算约 **10 秒**。这里用标准做法：

```kotlin
val pending = goAsync()                       // 延长广播生命周期
CoroutineScope(SupervisorJob() + Dispatchers.IO).launch {
    try { /* 查库 + updateAppWidget */ }
    finally { pending.finish() }              // 必须成对调用，否则广播不会结束
}
```

三个必须的细节：
1. `goAsync()` 拿到的 `PendingResult` **必须** `finish()`，否则系统会认为广播泄漏；
2. 查库放在 IO 线程，主线程只做 `updateAppWidget`；
3. 整个刷新包在 `try/catch` 里，异常时渲染「读取失败」兜底视图——**组件崩溃不能影响主 App**
   （docs/01 FR-3.8）。

## 5. 组件声明与生命周期

### 5.1 声明（widget 模块 manifest）

```xml
<receiver
    android:name=".DueWordWidgetProvider"
    android:exported="true"
    android:label="@string/widget_label">
    <intent-filter>
        <action android:name="android.appwidget.action.APPWIDGET_UPDATE" />
    </intent-filter>
    <meta-data
        android:name="android.appwidget.provider"
        android:resource="@xml/due_word_widget_info" />
</receiver>
```

`exported="true"` 是硬要求：桌面启动器在另一个进程，必须能向我们发广播。

### 5.2 生命周期回调

| 回调 | 时机 | 本阶段处理 |
|---|---|---|
| `onEnabled` | 第一个实例被添加 | 打日志 |
| `onUpdate` | 每个实例需要刷新 | 查库 + 渲染 |
| `onDeleted` | 某个实例被删除 | 打日志（下一阶段在此清理按实例配置） |
| `onDisabled` | 最后一个实例被移除 | 打日志（下一阶段在此取消 WorkManager） |

## 8. 已知限制（第 12 阶段解决）

1. 只有 2×2 一种尺寸，没有 4×2 宽版；
2. 没有配置界面，无法按实例选择订阅哪些词库；
3. 主 App 内答题后，组件要等最多 30 分钟才更新（缺主动刷新）；
4. 跨天后计数不会自动归零（缺 WorkManager 定时任务）。

## 9. 第 12 阶段：数据同步已全部落地

上述 4 条限制中，③④ 与「实时性」已在本阶段解决。

### 9.1 四条刷新链路（全部可用）

| # | 触发源 | 时机 | 实现 |
|---|---|---|---|
| ① | 系统 `onUpdate` | 添加组件 / 开机 / 时区变更 / 每 30 分钟 | `DueWordWidgetProvider.onUpdate` |
| ② | 主 App 启动 | 种子数据写入后 | `DanCiJiYiApp` → `requestUpdate` |
| ③ | 主 App 写库后 | 作答 / 导入 / 手动添加完成 | `WidgetSync.notifyDataChanged()` |
| ④ | 每日 00:05 | 跨天归零 | `WidgetDailyRefreshWorker` + `WidgetRefreshScheduler` |

### 9.2 链路 ③：为什么用 `WidgetSync` 而不是让 ViewModel 拿 Context

```kotlin
object WidgetSync {
    private var appContext: Context? = null
    fun install(context: Context)              // Application 启动时调一次
    fun notifyDataChanged()                    // 业务侧调它，失败静默
}
```

- ViewModel 拿不到 Context，也不该知道 AppWidget 存在；
- 刷新小组件是**附带效果**，失败必须静默——不能因为组件出问题让主流程抛异常；
- 三个调用点：`ReviewViewModel.answer` 成功后、`ImportViewModel` 导入完成后、手动添加成功后。

### 9.3 链路 ④：跨天为什么必须单独做

`updatePeriodMillis` 的系统下限是 **30 分钟**，且 Doze 下会被推迟到几小时后。
如果不单独定时，用户第二天早上看到的很可能还是昨天的数字。

```kotlin
PeriodicWorkRequestBuilder<WidgetDailyRefreshWorker>(1, TimeUnit.DAYS)
    .setInitialDelay(millisUntilNext(LocalTime.of(0, 5)), MILLISECONDS)
enqueueUniquePeriodicWork(NAME, ExistingPeriodicWorkPolicy.UPDATE, request)
```

- 用 `enqueueUniquePeriodicWork` + `UPDATE`：重复登记不会堆积任务；
- 初始延迟算到「下一个 00:05」，避免装完 App 立刻跑一次又等 24 小时。

### 9.4 一致性验证方法（对应本阶段第 4 项产出）

两种查询路径，必须得到同一个数：

| 路径 | 查询 |
|---|---|
| 小组件 | `WordRepository.observeDueCount(now)` —— 全库到期词数 |
| 列表页 | `observeWordbooks(now).sumOf { it.dueCount }` —— 各词库到期数求和 |

App 主界面新增「**小组件数据自检**」按钮，同时执行两条查询并弹窗对比：

```
数据一致 ✓
小组件读取（observeDueCount）：12 词
列表页合计（各词库 dueCount 求和）：12 词

两者走同一 Room 实例与同一份 db 文件，理论上必然相等。
```

若两者不等，说明存在「按词库过滤条件不一致」或「归档词库未排除」之类的逻辑漏洞。

### 9.5 占位样式（失败 / 无数据）

| 状态 | 标题 | 数字 | 副标题 | 附加行 |
|---|---|---|---|---|
| 有到期词 | 今日待复习 | `12` | 个单词 | 下一个：abandon |
| 今日已完成 | 今日已完成 | `✓` | 明天继续 | — |
| 没有词库 | 还没有词库 | `＋` | 点此导入 | — |
| 读取失败 | 读取失败 | `--` | 点此打开 App | 错误摘要（截断 24 字） |

三种非正常态都**保持可点击**（跳主 App），避免用户对着死组件无从下手。
