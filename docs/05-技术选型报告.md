# 技术选型报告

> ⚠️ **技术栈变更说明（第 15 阶段补记）**：本文第 2、4 节关于 **Jetpack Compose** 的选型论证是
> **第 2 阶段的历史方案**。第 6 阶段按课程任务要求，界面已改为 **View 体系 + RecyclerView**
> （Activity + RecyclerView + ListAdapter/DiffUtil）。变更不影响本文其它结论：分层架构、
> Room/StateFlow/WorkManager/AppWidget 的选型与排除清单仍然成立，仅「UI 用 Compose 而非 View」
> 这一条作废。实际技术栈见 `docs/09 §1.3`。

**文档版本**：v1.0（第 2 阶段产出，对应提交 #2）
**选型原则**：① 只用 Kotlin + Android 原生 Jetpack，**零跨平台框架**；② 不引入大纲外的主流框架（Hilt / RxJava 等），降低答辩被追问的风险；③ 依赖数量最少化——每增加一个库都要能说出「不用它会多写多少代码」。

---

## 1. 选型结论速览

| 层次 | 选型 | 一句话理由 |
|---|---|---|
| 架构模式 | **分层 + MVVM + 单向数据流（UDF）** | 状态单一来源、可测试、Compose 天然适配 |
| 模块划分 | **4 模块**：`:app` / `:widget` / `:core-data` / `:core-domain` | 把算法与数据层从 UI 里摘出来，可独立单测 |
| 依赖注入 | **手写 `AppContainer`**（不用 Hilt） | 4 个模块、约 12 个依赖，手写 60 行搞定；Hilt 会带来 KAPT/KSP 增量编译负担与大纲外概念 |
| UI | **Jetpack Compose + Material3** | 状态驱动 UI，全状态渲染用 `when` 天然穷尽；已与需求方确认 |
| 导航 | **`navigation-compose`** | 传参强类型、深链支持、返回栈可控（小组件跳转要用） |
| 状态容器 | **`ViewModel` + `StateFlow`** | 单一 `UiState` 数据类；`StateFlow` 有 `distinctUntilChanged` 与初始值语义 |
| 事件通道 | **`Channel`（receiveAsFlow）承载一次性事件** | 避免 Snackbar / 导航事件在旋转屏后重放 |
| 持久化 | **Room** | 官方方案、编译期校验 SQL、支持 Flow 与迁移测试 |
| 异步 | **Coroutines + Flow** | 与 Room / WorkManager 原生集成 |
| 后台任务 | **WorkManager** | 每日提醒与跨天刷新的标准答案，非精确窗口自动降级 |
| 桌面组件 | **AppWidget + RemoteViews**（不用 Glance） | Glance 与「原生 Jetpack + 稳定交付」目标冲突，且 Compose 运行时体积不进组件 |
| JSON 解析 | **kotlinx-serialization** | 编译期生成序列化器、无需反射、体积小 |
| CSV 解析 | **手写状态机**（不用 opencsv） | 需要精确到「第几行第几列」的错误报告，第三方库的错误信息不满足 |
| 依赖版本管理 | **Gradle Version Catalog（`libs.versions.toml`）** | 版本集中、IDE 补全、避免各模块版本漂移 |
| 测试 | **JUnit4 + kotlin-coroutines-test**（`:core-domain` 纯 JVM） | 算法可确定性验证，无需模拟器 |

## 2. 架构模式

### 2.1 分层与数据流

```
┌───────────────────────── UI 层（:app）─────────────────────────┐
│  Compose Screen  ←—— collectAsState ——  ViewModel              │
│        │                                   │                    │
│        └── 用户事件（Intent/回调）———————→  ┘                    │
└────────────────────────────────┬───────────────────────────────┘
                                 │ 只依赖 Repository 接口与领域模型
┌───────────────────────────────▼───────────────────────────────┐
│                    数据层（:core-data）                        │
│  Repository（唯一真源）→ Room DAO / 导入解析器 / 调度器调用     │
└────────────────────────────────┬───────────────────────────────┘
                                 │ 依赖纯 Kotlin 算法与模型
┌───────────────────────────────▼───────────────────────────────┐
│                  领域层（:core-domain，零 Android）             │
│  艾宾浩斯-Δ 调度器 · 领域模型 · Clock/Random 抽象               │
└───────────────────────────────────────────────────────────────┘
        桌面组件（:widget）只接数据层，直接读 Repository，不经 UI 层
```

**单向数据流的具体约定**

1. 每个界面一个 `XxxUiState`（`sealed interface`），ViewModel 暴露 `StateFlow<XxxUiState>`。
2. 界面只发事件（`onSortChanged`、`onAnswer(quality)`），**不持有可变状态**。
3. ViewModel 收到事件 → 调 Repository → 数据库变化经 `Flow` 回流 → 重新拼装 UiState。
4. 一次性事件（Snackbar、导航、弹窗）走 `Channel<UiEvent>`，不进 `UiState`。

### 2.2 为什么是 MVVM + UDF，而不是别的

| 候选 | 判断 | 理由 |
|---|---|---|
| **MVVM + UDF**（选定） | ✅ | Compose 的 `state → recomposition` 与 UDF 完全同构；「全状态 UI」要求的所有分支都能用 `when(state)` 穷尽渲染 |
| MVI 全家桶（含 Orbit/Redux 类框架） | ❌ | 概念增量大于收益：本项目事件数 < 40/屏，Reducer 抽象只会让课设代码更难讲 |
| MVP（Presenter + 接口回调） | ❌ | 与 Compose 不匹配，需要手工桥接回调到状态，且无生命周期感知 |
| 直接在 Composable 里查数据库 | ❌ | 无法测试、重组时重复查询、状态散落 —— 直接违反「全状态 UI」与 NFR-8 |

### 2.3 为什么不用 Hilt

| 维度 | Hilt | 手写 AppContainer（选定） |
|---|---|---|
| 依赖数量 | 3 个库 + 注解处理器（KSP） | 0 个库 |
| 编译时间 | 增量编译明显变慢（KSP 全量扫描） | 无额外开销 |
| 学习/答辩成本 | 需要解释 `@Module`/`@InstallIn`/组件生命周期 | 一个 `object AppContainer { val db by lazy { ... } }` 讲 30 秒 |
| 可测试性 | 优秀 | 够用：构造函数注入 Fake Repository 即可 |
| 项目规模适配 | 中大型 | **本项目（4 模块、12 个依赖）完全够用** |

> 结论：这不是「Hilt 不好」，而是「本项目用不上」。若后续扩展到 8+ 模块或多人协作，再引入。

## 5. 明确排除的库与理由

| 库 | 为什么不用 |
|---|---|
| **Glance**（Compose 版小组件） | ① 与「原生 Jetpack 而非常规 Compose 全家桶」的表述有偏差，答辩需额外解释；② Glance 仍在演进，踩坑成本高于收益；③ 组件只需展示 3 个字段，`RemoteViews` + XML 三十行搞定 |
| **Hilt / Koin** | 见 §2.3，规模不匹配 |
| **RxJava / RxKotlin** | 协程 + Flow 已覆盖全部并发需求，双异步模型是纯负担 |
| **Paging 3** | 单词上限 50000、日常词库通常 < 2000，`LazyColumn` 全量加载 + 稳定 key 已满足 60fps；Paging 会引入 `RemoteMediator`/`PagingSource` 概念与额外测试成本 |
| **Retrofit / OkHttp** | 应用不申请 `INTERNET` 权限，纯离线 |
| **Gson / Moshi** | kotlinx-serialization 是 Kotlin 原生、编译期生成、无反射 |
| **opencsv / kotlin-csv** | 错误定位粒度不够（要精确到行列与原因），且多一层依赖 |
| **MPAndroidChart** | 统计图用 Compose `Canvas` 自绘即可，避免引入 View 体系的依赖 |
| **DataStore** | 本项目的「设置」需要与 Room 事务一起读写（如清空数据时同时重置设置），放数据库更一致；小组件的 2 个配置项用 `SharedPreferences` 已足够 |
| **Timber / 第三方日志** | 用 `Log` + 自定义 `Logger` 足够，且课设不该有外部日志上报 |

## 6. 架构决策记录（ADR）

### ADR-001：UI 采用 Compose，而非 View + XML

- **背景**：课程大纲按 View 体系授课，但需求方选择 Compose。
- **决策**：全量 Compose（例外：`:widget` 必须用 XML + RemoteViews）。
- **收益**：全状态渲染用 `when(state)` 天然穷尽；重组即刷新，无 `notifyDataSetChanged` 的漏刷问题。
- **代价**：与大纲表述不一致，需额外说明；列表性能需注意稳定 key 与 `derivedStateOf`。
- **兜底**：第 16 阶段交付一页《Compose 与 View 体系对照说明》（生命周期、`remember` vs `findViewById`、状态提升 vs `LiveData` observer），用于答辩问答。

### ADR-002：状态用 `StateFlow`，不用 `LiveData`

- **决策**：ViewModel 暴露 `StateFlow<UiState>`，界面用 `collectAsStateWithLifecycle()` 收集。
- **理由**：`StateFlow` 有明确初始值（强制处理 Loading 态，不会出现「首帧白屏」）；可与 `Flow` 操作符组合（`combine` 词库与到期数）；便于 `runTest` 做确定性测试。
- **代价**：需要理解 `stateIn(SharingStarted.WhileSubscribed(5000))` 的重放语义。

### ADR-003：一次性事件用 `Channel`，不塞进 `UiState`

- **决策**：`Channel<UiEvent>(BUFFERED).receiveAsFlow()`，界面 `LaunchedEffect` 收集。
- **理由**：Snackbar「已保存」、导航「去复习页」若放进 State，会在屏幕旋转/重组后重放，出现重复弹窗或重复跳转。
- **反例**：用 `SharedFlow(replay=0, extraBufferCapacity=1)` 也可，但在无订阅者时会丢事件；`Channel` 会缓冲，更适合「保存成功」这类必须被看到的事件。

### ADR-004：算法放 `:core-domain`，并对 `Clock` 与 `Random` 注入

- **决策**：`ReviewScheduler` 接受 `clock: Clock` 与 `random: Random` 作为构造参数。
- **理由**：AC-09 要求断言「5 分钟」「2.5 天后」这类具体值；若直接调 `System.currentTimeMillis()` 与 `Random.nextDouble()`，测试只能断言范围，无法验证边界；抖动开关（§5.5 of `docs/01`）也必须可关才能复现。
- **代价**：生产代码多两行传参。

### ADR-005：小组件不引入 Compose，且不与主 App 互相依赖

- **决策**：`:widget` 只依赖 `:core-data`；主 App 提供数据变更通知（`WidgetUpdater`），组件侧也有 `onUpdate` 与 WorkManager 兜底。
- **理由**：组件崩溃隔离（FR-3.8）；且组件不应把主 App 的 UI 依赖拖进系统进程的 AppWidget 宿主。

## 7. 风险与备选方案

| 编号 | 风险 | 触发条件 | 备选方案 |
|---|---|---|---|
| R-01 | **JDK 25 与 AGP 9.5 不兼容** | 第 3 阶段空壳构建报 `Unsupported class file major version` 或 AGP 报 JDK 版本要求 | ① Gradle Toolchain 指定 JDK 21/17（需安装 Temurin，约 180MB）；② 降级 AGP 至 8.x 并改 compileSdk 36（需联网装 platform）；③ 见 `docs/03` 记录后决策 |
| R-02 | Compose BOM 与 AGP 9.5 版本不匹配 | 编译期 Compose Compiler 报版本校验失败 | BOM 与 `kotlin.plugin.compose` 同步降/升一个版本；第 3 阶段以「最小可编译」为准则锁定 |
| R-03 | 首次 Gradle 同步需下载大量依赖，网络不稳 | 依赖下载超时（`dl.google.com` 已实测可达，但可能抖动） | 配置国内镜像（阿里云 Maven）作为 `repositories` 兜底；或在 `gradle.properties` 提高超时 |
| R-04 | API 37 上行为变更未知（如通知权限细则、后台限制） | 第 15/16 阶段权限降级实现异常 | 以 `targetSdk 37` 编译但行为按 API 33+ 分支处理；必要时在 manifest 声明兼容标志 |
| R-05 | `navigation-compose` 深链在组件跳转时返回栈异常 | AC-16 失败 | 改用显式 `Intent` + `FLAG_ACTIVITY_NEW_TASK` 打开 `MainActivity` 并带 extra，NavHost 读取 extra 而非深链 |

## 8. 依赖总数量与体量预算

| 项 | 数量 | 说明 |
|---|---|---|
| 生产依赖（`:app`） | 13 | 见 §4.1 |
| 编译期插件 | 3 | KSP、Compose Compiler、Serialization |
| 测试依赖 | 3 | JUnit4、coroutines-test、kotlin-test |
| 第三方（非 AndroidX/JetBrains） | **0** | 全部为官方或 JetBrains 出品，无第三方运行时 |
| 预期 APK 体积 | 6–9 MB | Compose 运行时约 3–4 MB，其余为资源与代码 |

> 「第三方运行时依赖为 0」是刻意维持的：课设答辩时被问「这个库为什么用」是最常见的扣分点，能不引入就不引入。
