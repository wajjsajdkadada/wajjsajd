## 2. 模块划分

```
:app            主 App（Compose UI + ViewModel + 导航 + WorkManager 调度入口）
:widget         P1 伴生模块（AppWidgetProvider + RemoteViews + XML 布局 + 配置 Activity）
:core-data      Room 数据库、DAO、Repository、导入解析器（Android 库模块）
:core-domain    艾宾浩斯-Δ 算法、纯 Kotlin 数据模型与时钟抽象（零 Android 依赖，可单测）
```

**依赖规则（单向，禁止反向与循环）**

```
:app      ──> :core-data ──> :core-domain
:widget   ──> :core-data ──> :core-domain
:app  ──> :core-domain（直接使用算法做参数预览）
:app  ✗   :widget          （互不依赖，避免把 AppWidget 运行时拖进主 App）
:widget ✗  :app            （小组件不引用任何主 App 类）
```

**为什么这样切**

- `:core-domain` 零 Android 依赖 → 算法可做纯 JVM 单元测试（NFR-8），答辩时 `./gradlew :core-domain:test` 现场跑。
- `:core-data` 被两个展示端共享 → 小组件能读到与主 App 完全一致的数据，不需要额外 IPC，也不会出现「两套数据源打架」。
- `:widget` 独立成模块 → 满足「主 App + 伴生模块」的形态要求，且落实「小组件崩溃不影响主 App」。

## 3. P1 伴生模块设计设想（桌面小组件）

### 3.1 设计目标

| 目标 | 说明 |
|---|---|
| 一眼可得 | 不打开 App 就知道「今天还有多少词」——这是背单词类应用最高频的信息 |
| 一键直达 | 点组件直接进复习队列，不经过列表层级点击 |
| 零配置可用 | 添加即生效，默认订阅全部词库；想细分再用配置界面 |
| 绝不拖垮主 App | 组件刷新异常内部捕获，主 App 不受影响 |
| 尺寸自适应 | 2×2 与 4×2 两套布局，不是简单缩放同一份 XML |

### 3.2 组件规格

| 尺寸 | 名称 | 布局内容 | 数据 |
|---|---|---|---|
| 2×2（2 行 2 列） | 今日复习 | 环形进度（待复习/上限）+ 大数字 + 下一个词拼写 + 「开始复习」文字按钮 | 待复习数、上限、队首词 |
| 4×2（2 行 4 列） | 今日复习·宽 | 左侧待复习数 + 右侧 3 个单词拼写（等宽排列）+ 进度条 | 待复习数、前 3 词 |

**空态与降级文案**

| 场景 | 2×2 展示 | 4×2 展示 |
|---|---|---|
| 无词库 | 「点此导入词库」 | 同左 |
| 今日已清空 | 「今日已完成 🎉」+ 明日到期日 | 「今日已完成」+ 明日词数预告 |
| 数据读取失败 | 「点此打开 App」 | 同左（不显示异常堆栈） |

### 3.3 数据契约

小组件只读、不写业务数据（唯一例外：点击跳转由主 App 处理）。

```kotlin
// :core-data — 供主 App 与小组件共用的只读契约
data class WidgetSnapshot(
    val dueCount: Int,          // 今日到期词数
    val dailyLimit: Int,        // 每日上限
    val upcomingPreview: List<String>, // 最多 3 个拼写
    val nextDueDateLabel: String,      // 明日到期日期文案，如「明日 12 词」
    val state: WidgetState,     // NORMAL / ALL_DONE / NO_WORDBOOK / ERROR
)

enum class WidgetState { NORMAL, ALL_DONE, NO_WORDBOOK, ERROR }

interface WidgetDataSource {
    suspend fun loadSnapshot(bookIds: Set<Long>): WidgetSnapshot
}
```

小组件进程内直接打开同一 Room 数据库（同一 `Application` 进程，非独立进程），实现 `WidgetDataSource`，避免跨进程同步。

### 3.4 刷新链路（三条）

```
① 数据变更驱动（实时，≤1s）
   主 App 写库 → Repository 发出 Flow 变更 → widget 模块的 WidgetUpdater
   → AppWidgetManager.updateAppWidget(appWidgetIds, remoteViews)

② 跨天驱动（每日 00:05）
   WorkManager 周期任务（PeriodicWorkRequest, 24h, 初始延迟到 00:05）
   → 重新计算 dueCount → 更新全部组件实例

③ 系统兜底
   AppWidgetProvider.onUpdate（系统每 30min 一次兜底 + 开机/时区变更）
   → 与②走同一刷新函数，保证幂等
```

**幂等要求**：三条链路都调用同一个 `refreshAllWidgets()`，重复执行结果一致，不产生副作用。

### 3.5 点击与跳转

| 点击区域 | 动作 | 实现 |
|---|---|---|
| 组件整体 | 打开复习队列 | `PendingIntent.getActivity` + Deep Link `dancijiyi://review` |
| 「开始复习」按钮 | 同上（显式 `Intent` 带 `FLAG_ACTIVITY_NEW_TASK`） | 显式路由更稳，不依赖深链解析 |
| 无词库空态 | 打开导入界面 `dancijiyi://import` | 深链 |
| 长按组件 | 打开配置界面 | `android:configure` 声明 `WidgetConfigActivity` |

**返回栈要求**：深链进入后 `NavHost` 的 `popUpTo(WordList)` 修正返回栈，按返回键回到首页（单词列表），不出现空白或直接退出。

### 3.6 配置 Activity

- 列出全部词库，多选（CheckBox），默认全选。
- 配置结果写入 `SharedPreferences`（key: `widget_books_<appWidgetId>`），移除组件时在 `onDeleted` 清理。
- 取消配置 → 组件不添加（`RESULT_CANCELED`，标准行为）。

### 3.7 权限与降级（组件侧）

| 情况 | 组件行为 |
|---|---|
| 无通知权限 | 组件完全不受影响（组件本身不需要权限），只是每日提醒不响 |
| 无精确闹钟权限 | 跨天刷新改为非精确窗口（±15 分钟），组件数字可能晚几分钟归零，可接受 |
| 应用被系统限制后台 | `onUpdate` 系统回调兜底；用户点击组件时也能触发一次刷新 |
| 数据库被清空 | 组件渲染 `NO_WORDBOOK` 空态，不崩溃 |

### 3.8 明确不做（控制风险）

- 不做组件内答题 / 输入（RemoteViews 集合与输入事件受限，返工风险高）。
- 不做组件的多个独立实例差异化配置缓存服务端化（纯本地 `SharedPreferences` 足够）。
- 不做锁屏组件 / 通知栏常驻组件（大纲未要求）。
- 不引入 Glance（会与「原生 Jetpack」表述冲突且增加调试成本，直接写 `RemoteViews`）。

### 3.9 组件验收要点

| 编号 | 判据 |
|---|---|
| W-01 | 桌面添加 2×2 与 4×2 各一个，数字与 App 内一致 |
| W-02 | App 内完成 1 次作答，组件计数 ≤1s 更新 |
| W-03 | 手动改系统时间跨天，00:05 后组件归零并显示「今日已完成」 |
| W-04 | 删空所有词库，组件显示「点此导入词库」，点击进导入页 |
| W-05 | 断网 / 后台受限状态下组件不崩溃、可点击 |
| W-06 | 移除组件后 `SharedPreferences` 中的配置键被清理（无残留） |
