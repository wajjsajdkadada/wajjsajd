## 2. 模块依赖规则

| 规则 | 说明 |
|---|---|
| `:app → :core-data → :core-domain` | 单向依赖，禁止反向 |
| `:widget → :core-data → :core-domain` | 小组件共享数据层 |
| `:app` 与 `:widget` 互不依赖 | 避免主 App 被 AppWidget 运行时污染，也避免组件依赖整包 |
| `:core-domain` 零 Android 依赖 | 纯 Kotlin/JVM，可直接 `./gradlew :core-domain:test` |
| 禁止 `:core-data` 反向依赖 `:app` | 数据层不得引用 UI 类型 |

**包名基线**：`com.dancijiyi.app` / `com.dancijiyi.widget` / `com.dancijiyi.data` / `com.dancijiyi.domain`（第 2 提交确定并写入 `libs.versions.toml` 与各模块 `namespace`）。

## 3. 分支规划

采用**主干 + 短生命周期功能分支**，与「16 次有意义的提交」这一硬要求兼容：每个阶段在自己分支上打磨，最终以 `--no-ff` 合入 `main`，保证 `main` 上能看到 16 个有语义的提交。

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 唯一长期分支，始终可编译、可打包 | 全程 |
| `feat/<主题>` | 单个提交对应的功能开发（如 `feat/wordbook-list`） | 合入后即删 |
| `docs/<主题>` | 纯文档变更 | 合入后即删 |
| `fix/<主题>` | 缺陷修复（答辩前回归用） | 合入后即删 |

### 3.1 提交与合并流程

```bash
# 1. 开分支
git switch -c feat/wordbook-list
# 2. 小步改造 + 自测（可编译、可运行）
./gradlew :app:assembleDebug
# 3. 提交（见第 4 节规范）
git add -A
git commit -m "feat(wordbook): 词库列表与全状态 UI"
# 4. 合入主干（保留分叉，便于看出「一次提交 = 一个功能」）
git switch main
git merge --no-ff feat/wordbook-list
git branch -d feat/wordbook-list
```

### 3.2 验收—推送工作流（本项目实际执行方式）

采用「本地提交 → 学员验收 → 推送远端」三段式，保证未验收的代码不进入远端 `main`：

| 阶段 | 动作 | 执行方 |
|---|---|---|
| ① 本地提交 | 每完成一块功能立即 `git add` + `git commit`，提交信息按第 4 节规范 | 开发辅助 Agent |
| ② 学员验收 | 审阅 `git show --stat`、`git diff HEAD~1` 与实机运行结果，确认「通过」 | 你 |
| ③ 推送远端 | 验收通过后 `git push origin main`，并在里程碑处打 tag | 开发辅助 Agent |

**硬性约定**

1. 未经验收的提交**一律不推送**；验收不通过则在原提交上 `git commit --amend`，或追加一条修复提交后重新走 ②。
2. 每个实验课里程碑验收通过后，打对应 tag（见 3.3）并推送。
3. 远端历史保持线性：推送前先 `git fetch origin`，必要时 `git rebase origin/main`。
4. 推送通道为 **SSH**（本机 HTTPS 到 GitHub 连接被重置，实测不可用），密钥 `~/.ssh/id_ed25519` 仅存本机。

## 4. 提交信息规范

采用 **Conventional Commits**，中文正文，一次提交只做一件事。

### 4.1 格式

```
<type>(<scope>): <简短标题，不超过 50 字，不加句号>

<正文：为什么改、改了什么、边界与限制，可多行>

Refs: FR-1.1, AC-02        # 可选，引用需求编号便于答辩追溯
```

### 4.2 type 取值

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 重构（行为不变） |
| `build` | 构建配置、依赖、Gradle |
| `docs` | 纯文档 |
| `test` | 测试代码 |
| `chore` | 杂项（仓库初始化、忽略规则） |
| `style` | 格式调整（不影响逻辑） |

### 4.3 scope 取值

`repo` / `app` / `widget` / `data` / `domain` / `ui` / `wordbook` / `wordlist` / `detail` / `import` / `review` / `algo` / `settings` / `work` / `perm` / `docs`

### 4.4 硬性要求

1. **禁止** `update`、`修改`、`提交`、`aaa` 这类无信息量的标题。
2. 每个提交必须**可独立编译**（不允许「先把代码提交了，下次补依赖」）。
3. 一个提交不同时包含「重构 + 新功能」；先重构再功能。
4. 正文必须写清**为什么**，不能只描述「加了个文件」。
5. 提交前自查清单（第 6 节）。

## 6. 提交前自查清单

每次 `git commit` 前逐条确认：

- [ ] 代码能编译：`./gradlew :app:assembleDebug` 通过（#2 之后）
- [ ] 单测通过：`./gradlew test`（#11 之后必查）
- [ ] 只做了一件事，标题能一句话说清
- [ ] 新增需求点已回写 `docs/01-需求规格说明书.md`（需求蔓延拦截）
- [ ] 没有 `println`、调试用 `TODO()`、注释掉的死代码
- [ ] 没有提交 `local.properties`、`keystore/`、`.apk`、`.iml`
- [ ] 中文文案走 `strings.xml`，不硬编码在 Compose 里（`#3` 起生效）

## 7. 工程与仓库约定

| 项 | 约定 | 原因 |
|---|---|---|
| 行尾 | 仓库内统一 LF，`.gitattributes` 强制 `text=auto eol=lf`；仅 `.bat` 用 CRLF | Windows 提交、跨平台不产生整文件 diff |
| 换行与编码 | 全部 UTF-8（无 BOM） | 避免中文乱码 |
| 文件命名 | 文档用中文名（便于提交课设材料）；代码用英文 PascalCase | 兼顾可读性与编译 |
| 忽略策略 | `.gitignore` 覆盖 `build/`、`.gradle/`、`.idea/`（保留 `codeStyles`）、`local.properties`、`captures/`、`*.apk`、`*.jks` | 只提交源码与文档 |
| 大文件 | 单个提交文件总大小建议 < 2MB；示例词库仅保留 40 词 | GitHub/Gitee 友好 |
| 签名 | `keystore/` 与 `signingConfigs` 密码一律不入库 | 安全 |
| README | 主线变化时同步更新「当前进度」表 | 便于答辩展示进度 |
